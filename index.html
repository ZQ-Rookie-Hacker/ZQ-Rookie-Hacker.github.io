OAuth authentication

post @ 2026-04-15

0x00.基础知识

OAuth诞生前：古老的"密码共享"时代

在OAuth诞生之前，互联网上几乎没有标准化的授权方案。当你想让一个第三方应用（比如一款帮你分析好友社交网络的工具）访问你在另一个平台（比如你的社交账号）上的数据时，唯一的办法就是把你的用户名和密码直接告诉它。但是，这样存在巨大的安全风险：用户与密码可能会被保存、滥用，甚至被恶意程序用来做任何事，而你毫无办法

后来，一些大型科技公司（比如Google、Facebook）意识到了这个巨大的安全风险，开始各自推出私有的授权方案，例如FlickrAuth和GoogleAuthSub。但这些方案彼此不兼容，开发者需要为每个不同的平台单独学习和适配，极其痛苦

OAuth 1.0：从"共享密码"到"安全授权"

为了解决这个”授权困境”，OAuth（开放授权）应运而生。它的故事始于2006年，当时Twitter的一位开发者Blaine Cook在为Twitter实现OpenID时，发现没有一个好的方案来安全地授权第三方应用访问Twitter的API。于是，他与Chris Messina等人一起发起讨论，最终催生了OAuth协议。

OAuth 1.0协议的核心思想是引入一个"令牌"（Token）的概念。它就像一把精心设计的、有时间限制的”临时钥匙”，第三方应用只需用这把"临时钥匙"来访问你的数据，整个过程完全不需要知道你的密码

OAuth授权过程中，有三个关键角色

  1. 用户：数据的拥有者，比如社交网站的会员
  2. 服务提供商：保存数据的地方，比如Google、微信
  3. 客户端应用：想要访问用户数据的第三方程序，比如一款分析社交好友的App

OAuth 1.0的安全性高度依赖于其复杂的加密签名。为了确保授权过程中的核心数据（如令牌、参数）在传输中不被篡改，开发者必须在客户端（Consumer）和服务提供方（Service Provider）之间对所有HTTP请求进行签名

1.签名的工作原理,其核心思想是服务提供方能够验证收到的请求，确实是由知道正确客户端密钥（Consumer Secret）的客户端发出的，并且在传输过程中未被修改

  1. 生成签名基础字符串：客户端将HTTP方法、请求URL以及所有OAuth参数（如oauth_consumer_key, oauth_token, oauth_timestamp, oauth_nonce）按字母顺序排序并拼接成一个长字符串
  2. 计算签名：使用客户端密钥（Consumer Secret）和令牌密钥作为密钥，对上述字符串应用哈希算法（如HMAC-SHA1或RSA-SHA1），生成最终的签名值
  3. 发送并验证：签名被放在请求头中发送。服务提供方收到请求后，用同样的方法和密钥计算出预期签名，与收到的签名进行比对，只有完全一致，请求才被认为是合法的

浏览器同源策略与CORS解析

post @ 2026-04-12

前言：为什么需要同源策略？

互联网诞生之初，浏览器允许任意网页随意访问其他网站的数据。这带来了巨大的安全隐患：恶意网站可以悄悄读取你在银行网站上的个人信息，甚至冒充你进行操作。为了解决这个问题，浏览器引入了 同源策略，作为一道基本的安全防线。

但同源策略过于严格，现代 Web 应用又需要合法的跨域通信（比如前端调用不同域名的 API）。于是，W3C 制定了 CORS，在保证安全的前提下，为跨域访问打开一扇可控的门。

本笔记将按照 “问题 → 解决方案 → 细节机制 → 安全风险” 的逻辑，为你彻底讲清同源策略与 CORS。

1. 同源策略：浏览器安全的基石

JWT

post @ 2026-04-10

0x.00.JWT基础知识

  1. 🧩 JWT 的核心结构

一个 JWT 由三部分组成，用 . 分隔：

部分 名称 说明
第一段 Header（头部） 包含令牌类型（typ: "JWT"）和签名算法（如 HS256、RS256）。Base64Url 编码。
第二段 Payload（载荷） 包含声明（claims），如主题声明（sub）、过期时间（exp）、签发时间（iat）等。Base64Url 编码。
第三段 Signature（签名） 对前两部分进行签名，防止篡改。

  1. 注册声明

    • 官方声明
      • iss (issuer)：签发方
      • iat (issued at)：签发时间
      • sub (subject)：主题（一般放用户唯一标识）
      • aud (audience)：受众
      • exp (expiration time)：过期时间
      • nbf (not before)：在此时间之前不可用
      • jti (JWT ID)：唯一编号，防重放
    • 公共声明（Public Claims）:由 IANA 统一登记维护，行业通用、无冲突风险，不属于官方注册声明但广泛使用
      • auth_time：用户实际完成身份认证的时间
      • nonce：随机值，多用于 OIDC 场景，防止重放攻击
      • azp：授权参与方，通常存储客户端 ID
      • scope：权限范围字段，定义令牌可访问的资源范围
      • client_id：调用接口的客户端唯一标识
      • sid：会话 ID，关联用户当前登录会话
      • at_hash：访问令牌哈希值，OIDC 中用于校验令牌一致性
    • 私有声明（Private Claims）:业务方自定义字段，无统一标准，JWT 渗透测试中最核心的篡改目标
      • role/roles：用户角色，常见值 user/admin/root
      • username：登录用户名
      • userId/uid/id：用户唯一标识 ID
      • admin：布尔型标识，true 代表管理员权限
      • permissions：权限数组，存储具体操作权限
      • email：用户邮箱
      • group：用户所属分组
      • is_admin：管理员权限标识

  2. ✅ JWT 的典型使用流程

    • 登录：客户端发送用户名/密码 → 服务器验证成功 → 生成 JWT 并返回。
    • 存储：客户端通常将 JWT 保存在 localStorage、sessionStorage 或 HttpOnly Cookie 中。
    • 请求：客户端在后续请求的 Authorization 头或是Cookie中携带 JWT
    • 验证：服务器收到 JWT 后，验证签名、有效期、issuer 等，从载荷中提取用户身份。

  3. 📦 JWT vs Session（传统会话）

特性 JWT Session
服务端存储 无状态（不存储） 有状态（存储会话数据）
扩展性 易于水平扩展 需要共享存储（如 Redis）
吊销能力 困难（需黑名单） 简单（删除会话记录）
载荷大小 较大（包含用户信息） 很小（仅 session ID）
  1. 流程图


实现身份认证依靠的是检查 令牌的完整性（未被篡改）和真实性（由服务器签发），就会设置JWT的比对机制

对称签名算法(HS256，即 HMAC+SHA256)：同一个密钥既用于生成签名，也用于验证签名。这个密钥必须绝对保密，不能让客户端或任何第三方知道。若服务器可以使用所存处的密钥成功对应客户端发来的jwt进行解密，则通过认证。

BloodHound食用

post @ 2026-03-23

1. 手册概述

BloodHound 是域渗透测试中核心的可视化分析工具，其预构建分析查询可精准定位域内高价值目标、攻击路径、高危权限配置与协议漏洞。本手册系统拆解所有预构建查询的核心用途、实战价值，并给出分阶段使用策略，帮助渗透测试人员高效利用查询结果规划攻击链路。

2. 预构建查询分类详解

2.1 域基础信息类（Domain Information）

查询名称 核心作用 实战价值 备注
Find all Domain Admins 列出Domain Admins组的所有成员 明确域内最高权限账号，锁定渗透最终目标 所有后续查询的核心参照目标
Map Domain Trusts 可视化域信任关系（父子域/外部域/林信任） 规划跨域渗透路径，找到从子域突破到父域的链路 需结合域控拓扑分析信任方向
Find Computers with Unsupported Operating Systems 查找运行已停止支持系统（Win7/2008/XP等）的主机 定位最易突破的初始攻击入口（漏洞多、补丁少） 优先作为初始打点的目标清单

2.2 危险权限类（Dangerous Privileges）

查询名称 核心作用 实战价值 备注
Find Principals with DCSync Rights 查找拥有DCSync权限的主体（用户/组/计算机） 拿到该权限可直接同步所有域账号哈希，控制整个域 域内最高危权限，优先级最高的攻击目标
Users with Foreign Domain Group Membership 查找属于外部域组的用户 作为跨域攻击入口，利用用户在其他域的权限突破边界 需结合域信任关系分析权限传递
Groups with Foreign Domain Group Membership 查找包含外部域成员的组 利用组权限传递特性，实现跨域横向渗透 重点关注高权限组（如管理员组）的外部成员
Find Computers where Domain Users are Local Admin 查找普通域用户为本地管理员的主机 横向移动核心入口，拿到主机权限后窃取高权限凭证 优先对这类主机进行横向打点
Find Computers where Domain Users can read LAPS passwords 查找可读取LAPS密码的主机 直接获取主机本地管理员权限，无需破解 LAPS为本地管理员密码管理工具，是高价值目标
Find All Paths from Domain Users to High Value Targets 生成从普通域用户到高价值目标的完整攻击路径 渗透核心导航，明确“从哪台机、用哪个账号”提权 初始渗透阶段首选查询
Find Workstations where Domain Users can RDP 查找普通用户可RDP的工作站 直接登录后提权、窃取凭证 优先选择核心业务人员的工作站
Find Servers where Domain Users can RDP 查找普通用户可RDP的服务器 服务器承载关键服务，易接触高权限账号 重点关注数据库、应用服务器
Find Dangerous Privileges for Domain Users Groups 查找域用户组的危险特权（如SeImpersonatePrivilege） 利用特权实现本地提权，获取系统权限 结合提权工具（如JuicyPotato）使用
Find Domain Admin Logons to non-Domain Controllers 查找域管理员登录过的非域控主机 窃取这些主机的凭证可直接拿到域管权限 最稳定的提权方式之一，优先分析

2.3 Kerberos 协议类（Kerberos Interaction）
